# 验证规则

## 1. 默认规则

1. 普通功能切片只执行足以拦截编译错误和直接相关回归的基础机器检查，随后立即交给用户手动验收。
2. 编译、类型检查和 lint 只能证明基础正确；交互是否符合预期由用户体验结论确认。
3. UI、启动、导航、输入、文件读写等可在目标车机手测的行为变化，构建成功后必须自动覆盖安装当前 Debug APK并确认应用基础运行状态，再列出具体手测路径；不强制 AI 代替用户判断视觉和连续交互体验。
4. 不能为了让测试通过而降低断言强度。
5. 手动验证必须具体到本轮改动路径，禁止泛泛要求整体回归；允许用户承担该路径的主要体验验收。
6. 项目启用多语言后，必须机械检查 locale JSON 可解析、key 集一致、值非空、源码引用 key 存在，以及新增用户可见文案未绕过多语言主链。

## 2. 03桌面项目规则

1. 触发条件：纯文档或规则变化。动作：只执行相关文件 `git diff --check`；修改 skill 时追加 `check-skills`，修改项目总纲或验证入口时追加 `check-project-ready`。验证入口：`docs/testing/验证矩阵.md`。边界：不运行 Android 构建、环境检查或业务 smoke。
2. 触发条件：普通代码、资源或 Manifest 切片。动作：默认运行 `assembleDebug`；命中已有直接相关单测时追加对应测试。验证：任务成功。边界：不默认运行完整单测、Lint 或全量回归。
3. 触发条件：本轮产生可在目标车机手测的 Kotlin、资源、Manifest 或 Gradle 行为变化。动作：基础构建通过后执行 `./scripts/install-debug-to-device.sh`，核对设备和固定 APK 后覆盖安装，并确认 `com.tcrrry.desktop` 的进程与悬浮服务存在。验证：脚本成功输出安装、启动、进程和服务状态。边界：纯文档、只读查询、纯测试和纯 Git 操作不安装；设备离线或基线不符时必须报告客观阻断，不得改投未知设备。
4. 触发条件：设备验证会安装其它 APK、卸载、清数据、授权、重启或改设置。动作：先确认精确目标、数据影响和恢复方式；自动回归默认使用可删除测试包。用户在当前任务中明确指定普通第三方应用的精确包名并要求卸载时，人工门禁即视为打开，恢复 APK 核对无误后应执行真实卸载，不得以自动测试或调试阶段保护为由拒绝。验证：执行前后对比包、权限与设置状态，并确认恢复 APK 的包名和完整性。边界：本项目自身 Debug APK 的无清数据覆盖安装已获得长期授权；不得自动选择真实业务应用作为破坏性样本，也不得为 `03歌词` 或其它普通第三方应用建立永久卸载保护。
5. 触发条件：用户完成任一功能切片的手动体验。动作：记录反馈；有问题则修复受影响切片，无问题即可进入下一项或按用户指令提交。验证：用户明确反馈当前行为。边界：不要求等待整个 V1，也不因一次反馈重跑无关回归。
6. 触发条件：里程碑收口、准备提交/发布、高风险系统能力变更或用户明确要求完整验证。动作：执行 `testDebugUnitTest lintDebug assembleDebug`，并按本次范围选择真机 smoke。验证：记录真实结果。边界：完整验证只在这些触发条件下执行，不成为日常切片门禁。
7. 触发条件：用户明确要求验证固定车机上的系统 Intent，或里程碑验收命中确认页/安装页。动作：在真机同时核验窗口的实际 touchable region 与一个可逆的真实触摸结果，不能只凭画面出现判定通过。验证：系统窗口获得完整可触摸区域，且取消/确认的目标动作符合预期。边界：若固件对某个公开入口的可见页面产生错误触摸区域，改用同一公开系统能力的可操作入口，不接私有接口或触摸模拟。
8. 触发条件：新增或修改从抽屉打开的顶层窗口。动作：先跑 `StandardFloatingWindowLaunchCoordinatorTest`，再覆盖安装；测试必须覆盖 `window_mode=0/1` 直启、`2/3` 先 HOME 后等待标准浮窗占用消失、未知值失败与所有清理分支。用户最小手测分别从充电 ADAS 卡片和一个已占用的标准浮窗打开目标窗口。验证：仅 ADAS 时不误拦截；旧系统设置、行车记录仪、账号或应用中心窗口不回弹；连续点击不重复打开，失败或超时后仍可再次操作。边界：安装流程内部需要返回结果的授权页只验证能回到当前安装任务，不要求回桌面。
