# AI 协作规则

## 1. 默认规则

1. AI 必须先读取根 `AGENTS.md` 和命中任务的路由文档。
2. 低风险缺字段任务可以合理假设并推进，高风险任务缺范围、完成标准或人工门禁时必须追问。
3. 发现同类问题第二次出现时，不只修当前问题，还要沉淀规则、测试、skill 或 hook。
4. 收尾必须说明实际验证和剩余最小人工确认。
5. 不把一次会话的临时判断提升为长期架构结论。
6. 发现适合所有新项目默认具备的能力、skill、规则、检查或文档槽位时，必须记录为候选通用能力；确认跨项目通用后通过 `template-feedback` 回流到本地模板源 `/Users/q/Documents/Projects/NewProject`，不能让复制后的项目把自己当作模板源。
7. 当前工作区无法访问本地模板源时，交付说明必须标记“待回流本地模板源”，并写清候选内容、证据、去专有化要求和建议落点。
8. 创建或更新项目级 skill 时必须使用 `skill-authoring`，并同步能力池、验证矩阵和进度记录。

## 2. 03桌面敏捷协作节奏

1. 触发条件：进入 V1 代码、资源或 Manifest 施工。动作：先读取已确认的 V1 方案，在同一个施工对话内连续完成整个 V1，在既有分层内解决根因，不保留临时旁路、重复真值或仅为演示存在的代码。验证：所有物理文件、状态流和测试都能从方案追溯。边界：除非出现必须由用户操作的系统门禁或客观阻断，不因上下文规模主动拆成多个对话。
2. 触发条件：组织 V1 施工顺序。动作：只设置 3 个内部技术检查点：①悬浮抽屉、手势、前台服务与恢复；②应用枚举、隐藏自身、启动、网格、排序、卸载与事件刷新；③APK 安装、快捷控制、性能、异常恢复与整体收口。验证：依赖顺序与 V1 物理边界一致。边界：检查点不是独立交付阶段，不请求用户逐点验收，也不创建检查点提交。
3. 触发条件：到达内部技术检查点。动作：运行该检查点相关自动检查、测试和 Debug 构建；车机在线且能力可运行时自动覆盖安装并执行最短主路径 smoke，修复失败后立即继续下一检查点。验证：构建、安装、启动或目标状态均有可观测结果。边界：不得为了连续施工忽略失败；文档、只读查询和纯 Git 收尾不触发安装。
4. 触发条件：3 个内部技术检查点全部完成。动作：运行完整 V1 自动验证与构建，覆盖安装最终 Debug APK，执行最短全链路 smoke，然后一次性交给用户做更广的视觉、连续操作和真实车辆场景体验。验证：用户明确反馈问题或确认无问题。边界：用户体验验收不能替代 AI 在当前环境可完成的编译、相关测试、安装和主路径 smoke。
5. 触发条件：用户反馈问题。动作：继续定位根因、定点修复、重新构建安装并重复受影响检查点与最终最短闭环。验证：反馈现象消失且未破坏 V1 不变量。边界：不得为赶进度叠加临时特判。
6. 触发条件：用户确认无问题、明确要求提交，或任务开始时已经明确授权整个 V1 完成后提交。动作：使用 `task-closeout` 复用有效验证、更新进度并只提交授权范围。验证：交付中提供提交哈希和未推送/未发布状态。边界：内部检查点不继承提交授权，也不得产生中间提交。

这套节奏是 `03桌面` 当前设备、用户验收方式和开发阶段的项目事实，不作为 `NewProject` 的跨项目默认规则回流。
