# 多车型适配工作顺序

## 1. 文档定位

1. 本文记录 `03桌面` 将来适配其它 Android 车机时的统一工作顺序，供出现明确车型需求后重新启用。
2. 当前状态为备用方案，不代表项目已经启动多车型适配，也不改变当前 V1 仅面向 `S56_HQX` 的产品与验收范围。
3. 本文只规定先后关系和阶段产物。具体车型的技术锚点、算法阈值、权限边界和测试用例，必须在取得该车型真实证据后另写专项施工方案。
4. `03歌词` 不属于本仓库；如果未来适配同一车型，可以复用本文的调研顺序和车型事实，但必须在其自身项目中独立落地。

## 2. 总体原则

1. 先确认车机能做什么，再研究原车长什么样、如何响应事件，最后才决定软件如何实现。
2. 车型适配必须同时覆盖三条主线：系统能力、视觉设计、行为事件。只调整分辨率或缩放现有界面不算完成适配。
3. 优先用车型配置表达差异；只有配置无法表达的系统能力和事件来源，才新增厂商或车型适配器。
4. 统一的是业务事件的含义、优先级和处理结果，不强求不同车型提供相同的底层信号。
5. 不采用“一车型一套业务逻辑、一车型一个长期分支”的方式扩展产品。

## 3. 工作顺序

### ① 车机能力摸底

确认 Android 版本、芯片与性能、屏幕参数、APK 安装条件、悬浮窗口、后台运行、开机恢复、应用启动、媒体会话和可公开读取的系统状态。先判断完整适配、基础兼容和明确不可实现的边界。

阶段产物：车型能力档案。

### ② 原车 UI 分析

在原车桌面、应用中心、地图、媒体、设置、浮窗、倒车和安全提示等典型场景中，分析屏幕分区、安全区域、尺寸、颜色、字号、图标、间距、圆角、透明度、层级、动画和组件形态。

阶段产物：原车 UI 证据与车型视觉档案。

### ③ 原车事件与交互分析

分析原车在桌面、地图、标准浮窗、ADAS、倒车、息屏、前后台和媒体变化时如何切换状态，确认每类事件的触发条件、优先级、持续时间、结束条件和恢复目标。

`window_mode` 一类信号应先解释成统一的业务状态，再由车型适配器接入。不同车型可以使用不同的底层键、公开接口或事件来源，但进入 `03桌面` 后必须保持同类事件的判断、互斥、恢复和失败处理一致。

阶段产物：车型行为档案与事件映射表。

### ④ 制定车型适配方案

结合前三阶段证据，确定该车型采用基础通用模式、车型配置还是专用适配器，并明确功能范围、视觉方案、事件状态流、安全边界、性能预算和验收标准。没有真实证据的能力不得写成已支持。

阶段产物：该车型的专项施工方案。

### ⑤ 跑通基础功能

先完成安装、启动、权限、前后台存活、应用枚举、抽屉开合和应用启动等最小闭环。此阶段只证明产品能够在目标车机上可靠运行，不提前宣称视觉或原车联动已经适配。

阶段产物：可运行的基础兼容版本。

### ⑥ 完成界面与交互适配

依据车型视觉档案实现布局、位置、尺寸、颜色、透明度、组件、动效、触摸区域和安全避让，使软件与原车界面保持一致的视觉层级和操作习惯，而不是直接缩放现有 `S56_HQX` 界面。

阶段产物：车型视觉与交互实现。

### ⑦ 完成系统行为与事件适配

把车型原始信号转换为项目内部统一事件，并接入既有状态协调主链。桌面、地图、浮窗、ADAS、倒车、息屏和媒体等同类场景必须遵守统一的优先级、互斥、恢复、超时和失败语义。

阶段产物：车型系统适配器及事件闭环。

### ⑧ 真车场景验收

在目标真车上覆盖启动、桌面、地图、媒体、浮窗、倒车、息屏唤醒、熄火重启、连续操作和异常恢复。功能稳定性与原车视觉融合必须分别验收，不能用编译通过或模拟器画面代替真车结论。

阶段产物：真车验证记录、已知限制和兼容等级。

### ⑨ 固化并复用车型成果

将验证后的系统能力、视觉 token、事件映射、适配器和验收结果沉淀为可复用车型资产。后续同系统、同平台或同一厂商车型先继承已有资产，再依据真实差异增量调整。

阶段产物：车型配置、适配器、兼容矩阵和后续复用入口。

## 4. 启用条件

1. 出现明确车型、可联系的真实用户和可重复的实际需求。
2. 能取得目标车机的只读能力报告、关键场景 UI 证据和真车验证反馈。
3. 项目决定扩大当前单车型产品范围，并为该车型建立独立专项方案和验收基线。
4. 任一条件未满足时，本文继续作为备用资料，不提前扩张当前代码和权限范围。

## 5. 一句话执行顺序

车机能力摸底 -> 原车 UI 分析 -> 原车事件与交互分析 -> 制定车型适配方案 -> 跑通基础功能 -> 完成界面与交互适配 -> 完成系统行为与事件适配 -> 真车场景验收 -> 固化并复用车型成果。
