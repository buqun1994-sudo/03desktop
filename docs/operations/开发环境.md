# 开发环境

## 1. 逻辑依赖

1. JDK 17；本机路径写入已忽略的 `android-env.local.properties`，不进入可提交文档。
2. Android SDK：需要 Platform `android-34`、Build Tools `34.0.0`、Platform Tools 和 Command-line Tools。
3. Gradle：仓库内保留 Wrapper，版本 `8.2`；依赖缓存位于用户 Gradle 目录，不复制进仓库。
4. ADB：优先使用 Android SDK 的 Platform Tools；只有首选 ADB 无法连接且完成只读状态确认后，才用 `ANDROID_ADB` 指定备用二进制。禁止同时启动冲突的 ADB Server。

## 2. 本机配置

1. `local.properties`：至少包含 `sdk.dir=<本机 Android SDK 绝对路径>`，已被 Git 忽略。
2. `android-env.local.properties`：可选，包含 `java.home` 和 `adb.fallback`，已被 Git 忽略。
3. 可提交示例：`local.properties.example` 与 `android-env.example.properties`，不得包含个人电脑路径。
4. 签名字段示例：`keystore.properties.example`；真实 `signing.properties`、`keystore.properties`、`*.jks`、密码与证书均被忽略。

## 3. 检查与构建

1. 只检查工具链：`./scripts/check-android-env.sh`。
2. 同时检查目标车机：`./scripts/check-android-env.sh --device`。
3. 日常功能切片构建：`./scripts/gradlew-jdk17.sh assembleDebug`。
4. 里程碑、提交/发布准备或明确要求的完整构建：`./scripts/gradlew-jdk17.sh testDebugUnitTest lintDebug assembleDebug`。
5. 检查项目配置与权限白名单：`node scripts/check-android-config.mjs`。
6. 只读检查车机公开能力：`./scripts/check-device-capabilities.sh --package <普通第三方应用包名>`。
7. 构建成功后安装当前 Debug 包并检查基础运行：`./scripts/install-debug-to-device.sh`。

## 4. 车机连接

1. 开发连接地址：`192.168.0.203:5555`；它只用于安装、日志与真机验证，不是产品运行依赖。
2. 连接前先运行 `adb devices -l`；若设备已经是 `device`，不要切换或重启 ADB Server。
3. 本项目自身 `app/build/outputs/apk/debug/app-debug.apk` 的无清数据覆盖安装已获得长期授权：凡代码、资源、Manifest 或 Gradle 改动产生可手测行为，构建成功后默认执行。脚本必须显式核对设备基线和固定包名，环境检查脚本仍保持只读。
4. 安装其它 APK、清除数据、重启车机、授予权限、发起卸载和修改设置仍属于逐次人工门禁，不得由安装脚本隐式执行。

## 5. 构建产物与隐私

1. `local.properties`、本机工具路径、Gradle 缓存、APK/AAB、Lint 报告、日志、截图与录屏不提交。
2. Debug APK 仅用于开发；release keystore 创建、发布 APK 生成、安装到正式车机和分发均需要明确指令。
3. 当前没有部署或上线流程；Android 安装不等于产品发布。

## 6. staging 与 production 签名

1. Android 的 Debug 与 Release 都有签名；区别不在是否上应用商店，而在签名身份是否由项目长期控制。小规模网页分发仍使用独立 Release 证书，避免开发机 Debug 证书变化后用户无法覆盖更新。
2. 私密文件使用仓库外 `signing.properties` 与对应 JKS；字段结构见 `keystore.properties.example`。真实路径、密码和密钥不得写入 Gradle 源码、可提交文档或 Git。
3. 默认 Debug 继续使用开发机证书。测试包显式传入 `desktopSigningEnvironment=staging` 与 `desktopStagingSigningPropertiesFile`；正式包传入 `desktopProductionSigningPropertiesFile`。具体命令见 `docs/plans/03desktop包名与签名迁移方案.md`。
4. staging 证书 SHA-256 为 `BFB70DC15B54AD2F1B8ACD35FA26ECF552BF2EF21D416A44B7EEDA5E5E9EBAA9`；production 为 `D5ED175F00BD64BE4DE15ECC03B3EB3D1019305A89637E0A1C6B4DF314AA2417`。
5. 两个环境缺少各自材料时必须失败，不允许回落到开发机 Debug 证书。实际 APK 必须用 `apksigner verify --print-certs` 核对包名、单 signer、v2 和证书摘要。
6. 新包 `com.ninepointnine.desktop` 与历史包是两个应用，不能覆盖继承。当前已构建但未安装或分发；本机两份备份仍需在正式分发前分别转移到独立离线介质。
